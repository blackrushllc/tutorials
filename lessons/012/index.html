Writing code that works is only half the job - writing code that's easy to understand later on is just as important.

Example 1 | Writing Comments

  1. Click the button to open this program in a new editor tab.
  2. Then click the Run button or press F9 to run the program.

COMMENTS.BAS

// Comments start with // and are ignored when the program runs
// Use them to explain WHY your code does something, not just WHAT it does

LET taxRate = 0.08
// Applying local sales tax to the subtotal before checkout
LET subtotal = 50
LET total = subtotal + (subtotal * taxRate)

PRINT "Total with tax: "
PRINT total

// Good comments save you time later - bad or missing comments cost you time later

Good comments explain the reasoning behind your code, so future-you (or a teammate) doesn't have to guess.

Example 2 | Meaningful Variable Names

  1. Click the button to open this program in a new editor tab.
  2. Then click the Run button or press F9 to run the program.

VARNAMES.BAS

// Bad: short, unclear names that don't explain their purpose
LET x = 20
LET y = 5
LET z = x * y

PRINT z

// Good: descriptive names that explain what the variable holds
LET itemPrice = 20
LET itemQuantity = 5
LET orderTotal = itemPrice * itemQuantity

PRINT orderTotal

// Both blocks do the same math - only one is easy to understand at a glance

Descriptive variable names turn your code into something readable, almost like plain English.

Example 3 | Consistent Naming Conventions

  1. Click the button to open this program in a new editor tab.
  2. Then click the Run button or press F9 to run the program.

NAMING.BAS

// Picking one naming style and sticking with it makes code easier to scan
// Example: use camelCase for variables, and $ for string variables

LET playerName$ = "Justin"
LET playerScore = 0
LET playerLives = 3

PRINT "Player: "
PRINT playerName$
PRINT "Score: "
PRINT playerScore
PRINT "Lives: "
PRINT playerLives

// Mixing styles like PlayerName, player_score, and PLAYERLIVES in the same
// program makes it harder to predict what a variable is called
// Pick a convention early, and use it everywhere

Consistency matters more than which style you pick - it lets you predict variable names instead of hunting for them.

Example 4 | Refactoring Messy Code

  1. Click the button to open this program in a new editor tab.
  2. Then click the Run button or press F9 to run the program.

REFACTOR.BAS

// Before: works fine, but hard to follow
LET a = 15
LET b = 3
LET c = a * b
IF c > 40 THEN
    PRINT "big"
ELSE
    PRINT "small"
END IF

// After: same logic, cleaned up with comments and clear names

// Calculate order total and flag large orders for review
LET unitPrice = 15
LET quantity = 3
LET orderTotal = unitPrice * quantity

IF orderTotal > 40 THEN
    PRINT "Large order - flagged for review"
ELSE
    PRINT "Standard order"
END IF

// Same output, but now anyone reading it understands the business logic

Refactoring doesn't change what your code does - it changes how easy your code is to trust and maintain.
